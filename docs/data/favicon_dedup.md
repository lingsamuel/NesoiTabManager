# 列表 favicon 去重（图标表 + 内容指纹）

## 问题
保存列表时，每个条目都会把当时的 `tab.favIconUrl` 原样写进 `lists[].items[].favIconUrl`（见 `background/lists.js` 的 `tabToItem`）。
实测该字段的主要形态是 **`data:image/...;base64,...`**：同一张图标会被逐条完整重复保存。
`chrome.storage.local` 未申请 `unlimitedStorage`，默认配额约 10MB，于是"同一站点的多个标签页"就会成倍吃掉配额，
而它们在语义上只是同一张图片。

## 目标与非目标
- 目标：**同一个图标在 `chrome.storage.local` 里只存一份**，列表条目只保留一个短引用；读取与渲染的行为保持不变。
- 目标：**导出的 JSON 里同一个图标也只出现一次**——导出曾一度把引用逐条展开回 `favIconUrl`，文件里依旧重复 N 份，
  这不是"去重"该有的结果；现在导出走独立的紧凑格式（见下）。
- 目标：**不同子域名各自独立**——`mail.example.com` 与 `www.example.com` 即使同属一个站点，也可能有不同图标，不能被合并。
- 非目标：冻结历史（`discardSession`）、近期标签页（`recentTabs*`）、树结构快照里出现的 `favIconUrl` 不在本次范围：
  它们存放在 `storage.session`（浏览器重启即清空），生命周期短、体积可控。
- 非目标：不改变渲染路径与导入的兼容性（v1 旧文件照常导入）。导出格式从 v2 起改为紧凑结构，
  代价是旧版本扩展无法识别 v2 文件里的图标（列表本身不受影响）。

## 方案总览

**全局图标表 + 列表条目短键。**

- 新增 `chrome.storage.local` 键 `favIcons`：`{ [iconKey]: favIconUrl }`，**全局一张表**（跨列表共享）。
- 列表条目落盘时不再保存 `favIconUrl`，只保存 `iconKey`（短字符串）。
- **写盘归一化**：所有写列表的路径都先把条目里的 `favIconUrl` 换算成 `iconKey` 并登记进图标表，再裁剪表里的未引用项，最后一次性写入两个键。
- **读取解析**：所有面向 UI 的读取出口（`getLists` 消息）在返回前把 `iconKey` 解析回 `favIconUrl`。
  对外结构与改动前**完全一致**（只有 `favIconUrl`，没有 `iconKey`），因此管理页、弹窗、侧边栏保存清单的渲染代码不需要改动。

### 为什么不用"渲染时现取"
- Chrome 需要新增 `favicon` 权限并走 `_favicon` API；Firefox 没有对等的公开 API。
- 两端行为会不一致，且显示的是"浏览器当前图标库"而不是"保存当时的图标"。
- 结论：不做，仅在本文档末尾保留为备选记录。

## iconKey 规则

`computeIconKey(favIconUrl)` 的取值规则（**这是本方案的核心，直接决定去重粒度**）：

| `favIconUrl` 形态 | iconKey | 说明 |
| --- | --- | --- |
| 空 | `""` | 不写表项；读取解析为空字符串，前端回退占位图 |
| `data:...` | `d:<内容指纹>` | 按**图片内容**去重：同一张图无论出现在哪个站点、哪个子域名，只存一份 |
| `page-icon:<pageUrl>` | `p:<origin(pageUrl)>` | Firefox 会给出这种形态，URL 里带的是**页面地址**；归一到页面 origin，使同站点多页面共用一个条目 |
| 其它 | `u:<去掉 fragment 的 URL>` | 同一图标 URL 只存一份；不同子域名 / 不同 CDN 路径天然是不同的 key |

- **子域名为什么不会被误合并**：`p:` 用的是 `URL.origin`（协议 + 主机 + 端口），主机名完整参与比较；
  `u:` 用的是完整 URL；`d:` 用的是图片内容。三条路径都不会退化成"按可注册域名合并"。
- `page-icon:` 解析失败（内层不是绝对 URL）时退化为 `u:<原值>`，不做猜测。
- 只去 fragment（`#...`），**保留 query**：部分站点的图标 URL 用 query 区分版本（如 `?v=3`），去掉会误合并。

### 内容指纹的算法
- `data:` 形态用 **FNV-1a 64 位**（BigInt 实现）对完整字符串求值，输出 16 位十六进制。
- 选择理由：同步、无依赖、跨浏览器确定性一致；图标体积在 KB 量级，逐字符开销可忽略。
- 它是**去重指纹**而非安全哈希；表项只用于"同一张图复用一条记录"，实际碰撞概率在图标数量级下可忽略。
- 一次写盘内按 `favIconUrl` 做 Map 记忆化，避免同一张图被重复计算（例如一次保存 200 个同站点标签页）。

## 存储结构与数据流

### 存储
- `lists`：`Array<List>`，`List.items[]` 的条目为 `{ url, title, iconKey, savedAt }`（`favIconUrl` 不再落盘）。
- `favIcons`：`{ [iconKey]: favIconUrl }`，值是**真实出现过的原始 favIconUrl**（不做归一化改写，
  避免自造 `page-icon:` 地址带来的解析风险）。
- 两个键在**同一次 `storageSet`** 中写出，避免"列表已写、图标表未写"的中间态。

### 写盘（唯一写入口）
`background/lists.js` 的 `setLists(lists)` 负责：
1. 读取当前 `favIcons` 表；
2. 遍历新 lists 的全部条目做归一化：
   - 已有非空 `iconKey` → 保留；
   - 有 `favIconUrl` → 算出 key、登记进表（**同 key 后写覆盖，最新图标优先**）、删除 `favIconUrl`、写入 `iconKey`；
   - 两者都没有 → `iconKey: ""`；
3. 裁剪图标表：只保留新 lists 中仍被引用的 key（**顺带 GC**，见下）；
4. `storageSet({ lists, favIcons })`。
5. 模块内用一条 promise 链把上述"读表 → 归一化 → 裁剪 → 写盘"整体串行化，避免并发写互相覆盖。

### 读取
- 后台 `getLists` 消息出口调用 `resolveListsFavicons(lists, icons)`：把每个条目的 `iconKey` 换成 `favIconUrl` 并从结果里删除 `iconKey`。
- 解析不到（表项缺失/损坏）→ `favIconUrl: ""`，前端显示占位图，不报错。
- **硬性约束**：解析只发生在读取出口；任何写盘路径都必须使用原始存储结构（`iconKey`），绝不允许把解析结果回写。
  当前没有任何消息把整份 lists 回传后台，因此这条约束在现有代码里成立。

### 导出 / 导入
- 导出**不走** `getLists`（那会把 `iconKey` 逐条展开回 `favIconUrl`，同一个图标重复 N 份），
  而是走后台的 `exportLists` 消息，拿到"条目只带 `iconKey` + 顶层 `favIcons` 表"的紧凑载荷：

```json
{
  "version": 2,
  "lists": [
    { "id": "...", "name": "...", "description": "",
      "items": [ { "url": "...", "title": "...", "iconKey": "d:…", "savedAt": "..." } ] }
  ],
  "favIcons": { "d:…": "data:image/png;base64,..." }
}
```

- **导出时会对内存副本做一次归一化**：即使库里的旧数据还没迁移，导出的文件同样紧凑，且**不会写盘**。
- 导入同时支持两种文件：
  - v2（上面的结构）：条目只有 `iconKey`，文件的 `favIcons` 会并入本地图标表后再归一化（不并入会因"表里查不到"而清掉 key、图标全丢）；
  - v1（旧版本的自包含格式，条目内联 `favIconUrl`、没有 `favIcons`）：照常导入并自动转成 `iconKey`。
- 兼容性：v2 文件用旧版本扩展导入时列表能进来，但图标会丢（旧代码不认识 `iconKey` / `favIcons`）。

### 旧数据迁移
- 懒迁移：条目里仍带 `favIconUrl` 时读取出口原样返回、界面照常显示；下一次任何列表写操作
  （保存 / 重命名 / 删除 / 移动 / 导入）经过 `setLists` 时被归一化并落盘。
- 主动迁移：**扩展安装/更新（`onInstalled`）与浏览器启动（`onStartup`）时各检查一次**，
  发现还有旧结构就整份重写一遍。原因是懒迁移只在"下一次写列表"发生——用户升级后如果只是查看或导出列表，
  存储里的重复数据会一直留着，看上去就像"根本没去重"。
- 迁移是幂等的：判据是"条目里是否存在 `favIconUrl` 字段"，没有旧结构时连写盘都不做，
  因此不会每次启动都白写一遍。

### 图标表 GC
- 删除列表 / 删除条目 / 覆盖导入（replace）之后，图标表会留下不再被引用的条目。
- 策略：**每次写列表时顺带裁剪**——只保留新 lists 中被引用的 key。写盘本来就要遍历全部条目，多这一次扫描是 O(条目数)。
- 由于写盘已串行化，裁剪不会与并发写互相覆盖。

## 与侧边栏保存清单的关系
侧边栏「保存到列表」弹出清单只需要列表名与条目数（`SidebarApp.openSaveMenu`），
但它当前调用的是 `getLists`。去重后 `getLists` 会为渲染把图标**重新展开**，对"只要名字"的调用方是纯粹的浪费
（一次消息可能携带数 MB 的 base64）。
因此新增轻量消息 **`getListSummaries`**：返回 `[{ id, name, count }]`，侧边栏保存清单与网页悬浮组件改用它；
管理页与弹窗的渲染仍用 `getLists`（它们确实要显示图标），但**导出必须用 `exportLists`**。

## 边界情况
| 情况 | 行为 |
| --- | --- |
| `favIconUrl` 为空 | `iconKey: ""`，不写表项，界面占位图 |
| 图标表项缺失 / 存储被手工清理 | 解析为空字符串，占位图，不报错 |
| 同 key 但值不同（站点换了图标） | 后写覆盖（最新优先）；`d:` 由内容决定，覆盖是等价操作 |
| 同一个数据图片被不同子域名使用 | 按内容合并为一份（图片确实相同，符合预期） |
| 不同子域名的同名路径 | `u:https://a.example.com/favicon.ico` 与 `u:https://b.example.com/favicon.ico` 是两个 key，各自独立 |
| 列表为空 / 全部条目无图标 | 图标表被裁剪为空对象 |
| 导入文件带了本地没有的 `iconKey` | 表项随文件并入；若文件本身没带表，该图标显示占位图，导入不中断 |

## 验收要点
1. 保存同一站点的 N 个标签页后，`storage.local` 中 `favIcons` 只有 1 条，`lists` 里 N 条 `iconKey` 相同，且**没有** `favIconUrl` 字段。
2. `a.example.com` 与 `b.example.com` 各自保存后产生 2 条表项，管理页图标分别正确。
3. 管理页 / 弹窗 / 侧边栏保存清单显示的图标与改动前一致。
4. **导出的 JSON 里同一个图标只出现一次**（`favIcons` 一条 + 多个条目共用 key），且条目里没有 `favIconUrl`。
5. 旧数据（带 `favIconUrl`）在扩展更新/浏览器启动后自动迁移；迁移前直接导出，文件同样是紧凑的。
6. v1 与 v2 文件都能导入且图标正常显示；v2 文件在旧版本扩展里导入会丢图标（列表不受影响）。
5. 删除列表后，其独占图标从 `favIcons` 中消失；共享图标保留。
6. 旧数据（带 `favIconUrl`）在任意一次列表写操作后自动迁移。
